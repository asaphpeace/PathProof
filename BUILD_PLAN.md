# Sentinel Command — Step-by-Step Build Plan

Companion to `ARCHITECTURE.md` (the "what"). This is the "how and in what order" — scoped to the recommendation from planning: **build only Tier 0 (Cloud Posture Scanning) first, validate with real customers, then decide whether to continue.** Nothing below assumes Tiers 1–4 get built; Phase 4 is an explicit go/no-go gate.

---

## Feature roster — the graph/score-as-core principle, the starting XI, and what's rejected (not just benched)

This section exists so scope decisions don't get relitigated from scratch every time a new feature idea shows up. Core rule, established after reviewing ~30 candidate modules against Sendmarc/Pentera/Wiz and a further ~35-item "master checklist": **the Attack Path Graph and composite PostureScore are not a module competing for a roster spot — they're the tactical system every feature plays within.** A feature earns a place only if its output becomes a node, an edge, or a score input on that shared graph. If it would just produce its own disconnected report, it doesn't ship, no matter how good it sounds in isolation — a product that's individually-excellent parts assembled into a weaker whole (the "GM problem") is the specific failure mode this rule exists to prevent.

The XI was deliberately left at 10 positions with one spot open rather than padded (Section "Starting XI" above) — this fills that spot. Added directly in response to real feedback: Prowler/Cloudsplaining only ever see the cloud provider's control plane (IAM policies, security-group definitions) — neither reaches into the actual instance OS. A VPS with no cloud-provider API at all (the explicit ask that prompted this) has no control plane to scan in the first place; only host-level access (SSH, or the instance's own agent) can see it.

**GK position superseded:** "Detection Coverage" was originally scoped as a passive annotation on the graph ("would existing tooling have detected this path?"). A separate design conversation (prompted by a real incident at a company the user used to work for — caught in progress, before damage) asked a bigger question: not just "would we detect it" but "can the product actually watch for a specific principal doing something suspicious, follow their activity across systems, and build a real evidence trail." That fully subsumes the original GK scope and is a materially bigger idea, so it replaces it rather than sitting alongside it. Full design — four deliberate passes of gap-checking, each from a different angle (technical/architecture, cross-source correlation and alert-volume, privacy/governance/RBAC, and Sentinel's own operational blast radius) — lives in `ITDR_DESIGN.md`. Not built yet; that document is the design-phase output, schema and code haven't been written.

**FWD "Phishing Simulation" reimagined:** researching the originally-planned engine (Gophish) surfaced that its releases have stalled (no tag since September 2022) and that it's single-tenant by design — using it would mean building Command's own multi-tenancy layer on top regardless, undercutting the original "avoid building send/tracking from scratch" rationale. That prompted splitting the one feature into two, with clearly different consent bars: **Tier A — Spoof Proof** (no employees targeted, near-zero risk, absorbs the "Lookalike Domain Hunter" bench item, recurring monthly, rides the same consent weight as an Exposure scan) and **Tier B — Human Simulation** (the traditional employee click/credential test, rebuilt as a small custom pipeline on SendGrid rather than Gophish or a third party, recurring on a customer-set cadence stated directly in the signed Rules-of-Engagement document rather than requiring re-signature every cycle). Full design in `PHISHING_DESIGN.md`. Both tiers now built, backend and Command frontend.

**MID "Third-Party OAuth App Risk" queued next, and why this one specifically:** a review against real security-engineer/pentester job descriptions surfaced that only the IAM Privilege-Escalation Graph currently produces actual graph *topology* (nodes and edges) — Exposure, Host, and Phishing findings all land as `Finding` rows that feed the score and the report, but none of them resolve to a graph node (`Finding.asset_id` is always `None` outside the IAM slice). That means "the graph" — the thing Section 1 calls the actual differentiator — is really just the IAM slice today. An over-permissioned OAuth grant is structurally the same shape as an IAM escalation edge (a principal with an access path to a sensitive resource nobody's watching), so building it as a new `third_party_app` node type and `oauth_grant` edge type *on the existing graph*, not a disconnected tab, directly closes that gap and produces a visualization — unified cloud-infra-plus-SaaS-identity privilege mapping on one graph — that no competitor tool does (BloodHound does AD, Pacu/ScoutSuite do cloud IAM, SaaS-security tools do OAuth apps, always separately). Picked over Identity & Credential Hygiene specifically because it has no blocked external dependency (no customer-provisioned Auth0/Okta/Entra app needed) — buildable now. Simulate-the-Fix and MSP Portfolio Rollup are the natural next two after this, for the same reason: neither adds a new signal, both compound leverage on the graph this unblocks — Simulate-the-Fix makes it interactive, MSP Portfolio Rollup rolls it up across a managed portfolio.

### Bench — real, not cut forever, but no promotion without a specific trigger

- **Container/Kubernetes scanning** — promote when a real customer asks for EKS/AKS/GKE coverage
- **Ransomware Readiness** (backup/snapshot/versioning posture) — promote once the graph has data-store nodes to attach it to (near-free at that point)
- **SAST/SCA/SBOM/license compliance** — blocked on a structural prerequisite, not priority: these need source-code/repo access, a genuinely different consent model from `CloudAccountConnection`. Don't promote until that connection type is deliberately designed, not bolted on.
- **Automated audit evidence collection** — promote only if redesigned to attach evidence to specific graph nodes, not live in its own compliance tab
- ~~**Lookalike Domain Hunter**~~ — absorbed into Phishing Simulation's Tier A ("Spoof Proof"), see `PHISHING_DESIGN.md` §2.1 — no longer a separate bench item
- **Prospecting "one-click" assessment generator** (unauthenticated domain-in, branded report out) — standout idea, cheap (reuses V1's PDF pipeline), directly sales-enabling for the MSP motion; candidate to promote early
- **"What changed?" timeline** — cheap once scan-history diffing exists (Tier 1)
- **Automated DNS rollback ("undo")** — scoped, buildable, V1 already generates DNS records
- **WhatsApp-based ambient updates** — smart specifically for the SA/African market; promote alongside whatever notification-channel work happens first
- **AI Vendor/SaaS Terms Auditor** — as an enhancement to OAuth App Risk, not standalone
- **CISA KEV tagging** — cheap annotation on existing findings, low priority not zero

### Rejected outright — not benched, not sequenced, don't re-propose without new information

**Contradicts a decision already made for a specific reason:**
- Self-scraping dark-web credential dumps directly — `ARCHITECTURE.md` already specifies DeHashed/HIBP paid APIs specifically to avoid this legal exposure

**Solving the wrong way — the actual requirement doesn't need this much machinery:**
- ZK-proof baseline ledgers for tamper-evidence — a signed hash-chain over the existing `AuditLogEntry` table gets the same property at a fraction of the complexity
- M-of-N hardware-key consensus gates for remediation — gates a feature (auto-remediation) that doesn't exist yet

**Reverses a safety principle built deliberately this session:**
- Any "push to all tenants instantly, no per-customer consent" mechanism (global herd-immunity pushes, auto-deployed zero-day playbooks) — this is the Engagement consent-gate architecture's exact failure mode, and it's a real, famous disaster pattern (CrowdStrike's 2024 global outage), not a hypothetical
- Autonomous AI agents taking destructive action (isolating identities, "conversational virtual CISO" representing the product unsupervised) — reverses "destructive action requires human approval," present since the very first mockup
- Adversarial/generative AI pen-test swarms inventing novel exploit chains — this is Tier 5, deliberately deferred; companies with $100M+ in funding (Horizon3.ai, XBOW) are still solving the underlying verification-layer problem

**Legally/regulatorily a different business, not a feature:**
- "Legally binding" AI-generated regulatory documentation with no lawyer in the loop — liability generator if a customer relies on a wrong document during a real incident
- Any escrow/captive-pool mechanism that pays out on breach ("automated legal smart-contract escrow," "self-underwritten risk captive pools") — this is underwriting insurance, a licensed, capital-regulated industry; not something a SaaS product can casually add

**Describes an entirely different company:**
- OT/SCADA/critical-infrastructure security, sovereign/air-gapped defense deployment, national cyber-defense command centers — this is Claroty/Dragos/Nozomi's specialized business and defense contracting (ITAR, clearances, government procurement), not an extension of an MSP-first SMB security SaaS
- Operating your own Anycast DNS network / BGP hijack interception — this is becoming a Tier-1 network operator, competing with Cloudflare at a capital scale of billions; no scoped smaller version of this makes sense for this company
- On-demand labor marketplace for security analysts — a staffing business, not a feature

13. ✅ Done — **Lynis over SSH**. Consent-model decision (asked and answered): we generate the SSH keypair ourselves and the customer installs only the public key on a scoped read-only audit user they create — same "no stored secret" property as AWS role-assumption, and we never hold the customer's actual SSH credential. `HostConnection` model + migration, `crypto_service.py` (Fernet, keyed from `secret_key` via SHA-256 — first real use of encrypted-at-rest storage in this codebase; the AWS side never needed it), `host_scan_service.py`, `/host-connections` router, `'host'` added to `Engagement._VALID_TIERS`, `host_connection_ids` on `EngagementCreate`. `compute_tenant_cloud_posture_score` (name kept for existing callers) now blends `tier IN ('cloud', 'host')` findings into one posture bucket, matching the roster's single lineup entry for both lanes.

Built the way Lynis is actually documented to work instead: SSH in as the audit user, run `lynis audit system --quick --no-colors --report-file <tmp>` **on the target** (Lynis must be pre-installed there — now stated explicitly in the connection setup instructions), `cat` the report back, delete the temp file, parse `warning[]=`/`suggestion[]=` lines from Lynis' report.dat format.
